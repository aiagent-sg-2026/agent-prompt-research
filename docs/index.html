Use the leanest prompt that is still sufficient.

All A/B/C variants achieved 3/3 task success and zero unrelated edits. Lean A was most efficient on aggregate input tokens and latency; Structured B produced the smallest average diff.

This is descriptive n=3-tasks-per-variant evidence—not a universal claim that short prompts are better.

A practitioner rule

Prompt decision framework

  1. State the outcome. Include relevant domain context, allowed side effects, correctness contract, success test, evidence, and approval boundary.
  2. Remove noise. Delete repetition, stale examples, irrelevant tools, and process narration—while retaining details whose omission could change correctness, safety, semantics, approvals, or evidence.
  3. Add procedure selectively. Use ordered steps when sequence/completeness is itself required or representative evals show a reliability gap.
  4. Evaluate on representative work. Track success first, then scope/diff, latency, tokens, and retry proxies. Recheck after model, tool, runtime, or domain changes.

Interpret with care

Limitations

No statistical power, significance testing, or causal identification. The pilot uses one model/runtime, one run per task/variant, three small deterministic JavaScript tasks, and limited agent-domain diversity. Caching, order, environment effects, and runtime variability may affect resource measures. Provider usage and the retry field have the definitions documented in the report.

Reproducibility and links

Official agent runs are complete and raw inputs are frozen. Verify the aggregate and integrity manifest locally; do not rerun the official matrix as ordinary QA.
